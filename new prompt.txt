2. PROJECT CONTEXT

MajiSmart Zambia is an IoT-enabled water monitoring and community reporting system intended to address water shortages, inefficient water management, and difficulties monitoring water availability.

The system consists of three primary components.

A. Web application

The existing or planned website provides:

Water-monitoring dashboards.
Monitoring station and tank information.
Current water levels.
Water-level percentages.
Historical readings and charts.
Device connectivity status.
Automated alerts.
Community water-issue reports.
An interactive map.
Administrative tools for managing stations, reports, and alerts.
B. Android mobile application

The customer-facing mobile application provides:

Access to relevant water-monitoring information.
Water-level and station information.
Water-shortage and leakage reporting.
Optional photographs and location information.
A history of submitted reports.
Report status updates.
Synchronization with the website.
C. IoT hardware

The hardware is expected to use an ESP32 microcontroller and an ultrasonic water-level sensor.

The ESP32 measures the distance between the sensor and the water surface, derives water-level information, and may use LEDs to indicate normal, low, and critically low water levels.

It communicates over Wi-Fi with a backend or another supported ingestion mechanism.

The backend stores and validates readings and makes the data available to the web and mobile applications.

Intended technology direction

The intended backend direction is Supabase and PostgreSQL, with appropriate authentication, database security, and realtime synchronization.

The existing codebase is the source of truth for what has already been implemented. Verify the actual technologies before deciding how to proceed.

Do not replace existing technologies simply because you prefer a different framework.

8. BACKEND DATA MODEL

Design the data model based on verified requirements.

Evaluate the need for the following entities:

Profiles

Stores application profile information and a securely managed role assignment associated with the authenticated user.

Monitoring stations

Represents locations where water-monitoring infrastructure is installed.

Tanks

Represents individual water tanks, including the dimensions and configuration needed to calculate water levels.

Monitoring devices

Represents ESP32 devices and their station or tank associations.

Water-level readings

Stores measurements and the information necessary to interpret them reliably.

Alerts

Stores generated alerts, severity, affected tank, creation time, and acknowledgement or resolution state.

Community reports

Stores water-shortage, leakage, burst-pipe, tank-malfunction, and other community reports.

Report status history

Preserves meaningful transitions in report status and records the responsible administrator when applicable.

Add other tables only when justified.

Use proper:

Primary and foreign keys.
Constraints.
Indexes.
Timestamps.
Referential integrity.
Validation.
Unambiguous measurement units.

Consider high-frequency IoT writes when designing indexes and data-retention strategies.

Avoid premature complexity.

9. BACKEND SECURITY

Security must be designed into the implementation from the beginning.

Implement and verify:

RLS on exposed application tables.
Explicit role-based authorization.
Secure administrator provisioning.
User ownership restrictions.
Validated report submissions.
Validated sensor measurements.
Protected administrative actions.
Restricted file uploads.
Appropriate access to Realtime events.
Safe error handling.

Do not use editable user metadata as the authority for administrator privileges.

Do not trust a user ID supplied by the client when the authenticated session can establish the identity.

Customers must not be able to:

Promote themselves to administrators.
Change another customer's private reports.
Alter administrative report status fields.
Modify protected monitoring configurations.
Submit readings as an authorized hardware device.
Device ingestion

Investigate the most appropriate secure ingestion design for the observed hardware.

Prefer a server-side ingestion endpoint or another design that can authenticate each device independently of customer authentication.

A server-side endpoint may validate a provisioned device credential, validate the device-to-tank association, and insert the measurement into PostgreSQL.

Do not place the Supabase service-role key in:

Browser JavaScript.
Android application code.
Public configuration files.
ESP32 firmware.

If direct device-to-Supabase ingestion is proposed, justify its security model before implementing it.

Use the minimum necessary permissions.
