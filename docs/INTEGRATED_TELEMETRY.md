# Integrated telemetry and installation (local implementation)

This document supersedes the earlier standalone-geometry remarks in IMPLEMENTATION_PROGRESS.md. Changes have not been deployed or tested on hardware or PostgreSQL.

## Migration and compatibility

Review and apply Supabase migrations `20261031000004` through `20261031000006` with the project's migration process **before** deploying this API. They add `tank_installations`, `telemetry_metadata`, `report_case_events` and `tank_calibration_tests`, with indexes and API-only RLS. The local SQLite equivalent migrations in `BACKEND/database/migrations/002_installation.sql` through `004_calibration.sql` run idempotently at startup. Back up data and test on a disposable copy first. PostgreSQL startup does not automatically apply these newer migrations.

This is a deliberate telemetry breaking change: existing seeded/legacy tanks have no trustworthy geometry and cannot ingest until separately configured; unknown devices no longer self-register. The installation screen can configure a pre-existing unconfigured tank using newly measured geometry and a newly provisioned device. Existing name and station are retained, previous devices are revoked and detached, and reading history is preserved. A device on an already-configured installation can also be replaced. Do not invent calibration values. Legacy records have unknown provenance, and historical readings remain unchanged. Existing public installation-unowned infrastructure remains public for compatibility; assigned tanks are scoped in tank, station and alert endpoints. Audit other legacy endpoints and access patterns before production.

## API

* `POST /api/installations` (admin): creates a new tank, its installation and device atomically; or supply `existing_tank_id` to configure an existing unconfigured tank without overwriting its name or station. The old device is revoked and prior readings are retained. Fields: `name`, `tank_id_code`, `device_id`, `device_key` (24–256 characters), optional `owner_id`, `station_id`, `address`, `community`, `latitude`/`longitude`, `shape`, `height_cm`, `diameter_cm` or `length_cm` and `width_cm`, optional `nominal_capacity_l`, `empty_distance_cm`, `full_distance_cm`, `measurement_offset_cm`, `dead_zone_cm`, `tolerance_cm`, `sensor_model`, `mounting_position` (TOP only), `installer_notes`, thresholds and `provenance`. IDs and key must be unique/strong; use an independently generated cryptographically random credential per device. The API does not return the credential. Supply it over HTTPS only; never commit it. Reusing passwords or the legacy shared key is unsafe. Stored credentials use the existing SHA-256 hash scheme, which assumes high-entropy keys; per-device salt and rate limiting are future security work.
* `POST /api/installations/:id/device` (admin): replaces the device on an already-configured tank and revokes/detaches prior devices transactionally. Credentials are not returned. Historical readings retain their original device codes. Concurrent replacements have not been tested on PostgreSQL.
* `GET /api/installations` and `GET /api/installations/:id/calibration-tests` (admin) list configured installations and their recent calibration evidence.
* `PUT /api/devices/:device_id/credential` (admin): `{ "revoke": true }` or `{ "revoke": false, "device_key": "..." }`; a new key rotates the previous one. An unrevoked device is not automatically reconfigured.
* `POST /api/installations/:id/calibration-tests` (admin): `{ "distance_cm": 15, "manual_depth_cm": 10 }`. Saves a manual test and signed calculated-minus-manual depth error. `POST /api/installations/:id/verify-calibration` with `{ "max_error_cm": 1 }` requires the most recent test in each low (≤25%), middle and high (≥75%) depth band to pass. Recording a new test returns the installation to AWAITING_CALIBRATION pending review. Verification is an administrative decision, not proof that hardware is accurate; choose tolerance based on actual equipment. The installation screen can reopen a configured tank and display its recent calibration tests.
* `POST /api/iot/readings`, header `x-api-key`: `{ "device_id": "...", "tank_id": "...", "distance_cm": 15.5, "measured_at": "2026-10-31T12:00:00Z" }`. Timestamp is optional; when present it must be timezone-qualified and within five minutes of server time. The server uses receipt time for the current reading. The optional legacy depth, percent and status fields are ignored; raw distance and calculated depth, percentage and volume are separate. Invalid or uncalibrated geometry, sensor dead-zone/out-of-range distances, mismatched tank, unknown or revoked device are rejected. Configuration is initially AWAITING_CALIBRATION; estimates are explicitly labelled unverified until tests pass.
* `GET /api/my/tanks` and `/api/my/reports` require a user token. `GET/POST /api/reports/:id/case` are admin-only append-only case events; status transitions remain in the existing status-history endpoint. Original customer fields are unchanged.
* `GET /api/analytics/telemetry?from=YYYY-MM-DD&to=YYYY-MM-DD&tank=CODE` is admin-only. It uses receipt dates and groups readings whose installation provenance at ingestion was OPERATIONAL. Count is number of readings, not events or hours; mean/min/max use volume percentage and LOW/CRITICAL counts use recorded hysteresis condition. Unknown, historic, TEST and SIMULATED readings are excluded. Report analytics is separate and is not operational-only: only the three known seed IDs can currently be excluded.

## Measurement and realtime

All internal lengths use cm and volumes litres. Corrected distance = raw distance + measurement offset; depth = empty reference − corrected distance. Empty minus full must equal usable height. Vertical cylinder and rectangular volumes are linear in depth; horizontal-cylinder volume uses a circular segment and currently requires height equal to diameter. Nominal capacity is not used in the calculation. Valid measurements within configured tolerance are clamped to calibrated bounds; outside that range are rejected. Thresholds are volume percentage. Deterioration occurs at or below each threshold immediately; recovery requires the threshold plus hysteresis to be exceeded. WARNING is mapped to NORMAL in the old `current_status`/reading status fields to satisfy existing constraints; the new `current_condition` and telemetry metadata retain WARNING. Device offline state overrides last-known condition in customer displays. Sensor errors are rejected but are not yet persisted as sensor-fault events.

SSE is unauthenticated and now carries only invalidations, not record payloads; web clients refetch authorized data and refetch on reconnection. It remains process-local, with no replay, and Android currently refreshes manually rather than consuming SSE. Alert processing occurs after the telemetry transaction and is best effort. The device monitor uses `DEVICE_OFFLINE_TIMEOUT_SECONDS` (default 60). There is no guaranteed exactly-once delivery or ordering under concurrent device requests.

## Demo and firmware

Register a separate SIMULATED installation and its credential before running the CLI simulator. Set `IOT_API_KEY` in the local environment and pass `--tank=... --device=...` to `node FIRMWARE/simulator/iot_simulator.js`; the simulator uses the same authenticated endpoint. Do not use a real operational device credential for simulations. `DEMO_MODE` now selects SIMULATED installations only and still requires a matching configured key; it will not populate legacy seed tanks.

The ESP32 firmware filters five pings by median and requires three valid measurements, sends raw distance, reconnects Wi-Fi and retries by taking a new sample next interval. It requires an HTTPS URL and trusted CA PEM; no insecure TLS bypass is enabled. It does not queue failed samples, provide a signed timestamp, or report sensor faults to the backend. Arduino compilation and physical tests are outstanding. Local serial output is diagnostic; guard access to the device. For HC-SR04 use a 5V supply and a voltage divider on ECHO to protect the ESP32's 3.3V GPIO, common ground, and observe sensor minimum range/dead zone. Confirm the sensor supports the small container and water surface before relying on a reading.

## Known gaps

Map search uses the external OpenStreetMap Nominatim service and sends the search text to it; it may be unavailable or subject to its usage policy. Manual coordinates and map clicks remain available. There is no device-location button, geometry editing, owner self-service, controlled staff assignments, structured customer impact/time fields, broad fault/time/geographic analytics, or reliable report provenance yet. Android build, firmware compilation, actual PostgreSQL persistence, multi-process SSE and physical end-to-end tests have not been performed. Existing status and account flows require further security and UX review. Do not deploy these changes without migration, security review, hardware validation and regression testing.

The simulator sets `x-simulation: true`; ingestion rejects that marker for installations labelled OPERATIONAL or UNKNOWN. This is an accidental-contamination guard, not cryptographic proof of measurement origin: anyone holding a real device credential could omit the marker. Restrict access to credentials and networks and use separate devices/keys for simulation.

Report intelligence also groups the latest non-null administrative classification, severity and outcome per report, and submissions by station and month. These are administrator-entered case values, not sensor observations. Multiple event records do not multiply report counts. Unspecified fields remain unspecified; the original user-reported category remains separate.
